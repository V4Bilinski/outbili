## Story

**Como** engenheiro responsável pelo OUTBILI,
**quero** eliminar as duas últimas dependências de infraestrutura legada (o Cloudflare Worker `assertiva-proxy` e o n8n) dos fluxos de **enriquecimento raso Assertiva** e **busca de leads**, migrando o primeiro para uma Edge Function Supabase e removendo o vestígio do segundo,
**para que** o OUTBILI tenha 100% do seu backend de aquisição/enriquecimento sob o Supabase (sem CORS-proxy de terceiros, sem credenciais Assertiva no browser, sem n8n morto no código) e o epic Airtable→Supabase fique materialmente concluído.

## Contexto

- Estado pós-W3-08 + Camada 2 + LGPD (ver [`SESSION-HANDOFF-2026-05-24.md`](../migration/SESSION-HANDOFF-2026-05-24.md) e [`NEXT-SESSION-KICKOFF.md`](../migration/NEXT-SESSION-KICKOFF.md)): banco 100% Supabase (746 leads, 11 users), Airtable fora do runtime, deep enrichment (sócios) e redes sociais (Apify) em produção. **O n8n/Worker é o único vetor de infra legada restante.**
- **PASSO 0 cumprido:** o operador já rotacionou as credenciais Assertiva (CLIENT_ID/SECRET) e atualizou o secret no Supabase. Logo a validação E2E da Fase A pode usar credenciais válidas.
- **Modelo pronto (Fase A):** a Edge Function `supabase/functions/assertiva-enrich/index.ts` (W3-08, ACTIVE) já implementa OAuth2 server-side com cache de token no isolate, CORS e chamadas encadeadas à Assertiva. A `assertiva-proxy` replica esse padrão de auth/CORS expondo as 5 ações de enriquecimento raso.
- **Fase A — o que existe hoje** (`src/services/assertivaService.ts`):
  - 5 ações via proxy: `lookup-cnpj`, `get-decision-makers`, `lookup-cpf`, `lookup-phone`, `discover-endpoints`.
  - Roteamento atual: `WORKER_URL` (`VITE_ASSERTIVA_WORKER_URL`, primário) → `N8N_URL` (`VITE_N8N_ASSERTIVA_PROXY`, fallback) → bloco DIRECT (usa `VITE_ASSERTIVA_CLIENT_ID/SECRET` no browser, não funciona por CORS).
  - **O mapeamento de resposta (RAW Assertiva → domínio) permanece no service.** A Edge Function deve retornar o JSON RAW da Assertiva (`{ resposta, cabecalho, ... }`), exatamente como o Worker fazia — os mappers `lookupCnpj`/`getDecisionMakers`/`lookupCpf` já esperam `raw.resposta || raw`.
  - Consumidores (assinatura inalterada): `enrichmentService`, `pescaService`, `SearchPage`, `integrationHealthService`.
- **Fase B — o que existe hoje:**
  - `pescaService.ts` **já** faz busca completa via CNPJa: `searchViaCnpja` (→ `cnpjaService.searchOfficesPaginated`) → `deduplicateLeads`/`loadExistingDedup` → `savePescaToSupabase` (insert em `app.leads`). Em produção, funcional.
  - `src/hooks/useN8nSearch.ts` + `src/lib/n8n-webhook.ts` (`VITE_N8N_WEBHOOK_URL` → `n8n.bilinski.cloud/webhook/outbili-search`, scraping Google Maps) são um **caminho legado paralelo**. `SearchPage.tsx:274` instancia `const n8n = useN8nSearch()`. Decisão do operador: **remover o vestígio**, sem criar Edge Function `lead-search` (o PESCA já cobre).
- **Achado de segurança fora de escopo:** `VITE_CNPJA_API_KEY` está exposta no bundle (`cnpjaService.ts:3`). Registrar como pendência **W3-12** (mover CNPJa para Edge Function), NÃO tratar aqui.

- **Client Supabase:** `src/lib/supabase.ts` exporta `supabase` (schema `app`) e `supabaseAudit`. Para `functions.invoke`, usar o client `supabase`.
- **Padrão de retorno da Edge Function:** o Worker retornava o JSON RAW da Assertiva. NÃO mapear na função — os mappers do service esperam RAW (`raw.resposta || raw`, `raw.cabecalho?.protocolo`).
- **OAuth Assertiva:** `POST https://api.assertivasolucoes.com.br/oauth2/v3/token`, Basic `base64(CLIENT_ID:CLIENT_SECRET)`, `grant_type=client_credentials`. Cachear token no isolate (ver `assertiva-enrich`).
