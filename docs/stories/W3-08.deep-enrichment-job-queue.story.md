## Story

**Como** SDR usuário do OUTBILI,
**quero** que o re-enriquecimento profundo de um lead (grafo de sócios, telefones, WhatsApp pessoal) seja processado em segundo plano por uma fila, sem travar minha tela nem falhar com erro de rede,
**para que** eu clique "Reenriquecer", continue trabalhando, e os dados apareçam quando ficarem prontos — com a base inteira sendo mantida fresca aos poucos, sem estouro de custo.

---

## Contexto

- **Causa-raiz (validada 2026-05-26):** `assertiva-enrich` roda síncrona dentro do request HTTP e estoura o **wall-clock ~150s** do gateway Edge. Cascata serial de 4 chamadas Assertiva + 4×`delay(300ms)` por sócio (`supabase/functions/assertiva-enrich/index.ts:356-522`). Sintoma: `OPTIONS` 204 logado, `POST` nunca completa → `net::ERR_FAILED` no `socioService.runDeepEnrichment` (`src/services/socioService.ts:230`, sem AbortSignal).
- **Infra de fila já existe (parcial):** `app.enrichment_jobs` (status/priority/attempts/error/metadata), enums `enrichment_job_status` (queued/processing/done/failed/retrying) e `enrichment_priority` (realtime/high/normal), índice `enrichment_jobs_status_priority`, cron `enrichment-jobs-sweeper` (1/min, enfileira normal p/ leads com run > 7d, limit 50). Extensões `pg_cron` 1.6.4 + `pg_net` 0.20.0 + `supabase_vault` 0.3.1 disponíveis.
- **O que faltou:** **o worker (consumidor) nunca foi construído.** Os 746 jobs estão todos `queued` desde 20/05 (fila órfã). RLS de `enrichment_jobs` só tem `SELECT` para `authenticated`.
- **Leitura do grafo funciona:** os dados do W3-08 gravados em 23/05 (3 sócios do 4F CLINICA, WhatsApp, anti-filial) renderizam corretamente na CompanyPage. O bug é só no re-enriquecimento ao vivo.

## Acceptance Criteria

### AC-1 — RPC de enfileiramento (realtime)
- [ ] Migration cria `app.request_enrichment(p_lead_id uuid) returns uuid` SECURITY DEFINER.
- [ ] **Given** um usuário autenticado, **when** chama a RPC para um lead, **then** um job é criado/elevado a `priority='realtime'`, `status='queued'`, e o `job_id` é retornado.
- [ ] **Given** já existe job ativo (`queued`/`processing`) para o lead, **when** a RPC roda, **then** NÃO duplica — eleva a prioridade do existente para `realtime` (idempotente).
- [ ] EXECUTE concedido a `authenticated`; `enrichment_jobs` permanece sem INSERT/UPDATE direto para `authenticated` (só SELECT para polling).

### AC-2 — Dispatcher + worker cron
- [ ] Migration cria `app.dispatch_enrichment_jobs(p_budget_normal int default 3, p_enabled_normal boolean default true)`.
- [ ] Seleciona `queued` com `FOR UPDATE SKIP LOCKED`, ordem `priority` (realtime→high→normal) + `requested_at`; **realtime sempre processado** (sem budget), `normal` só se `p_enabled_normal` e dentro de `p_budget_normal`.
- [ ] Marca selecionados `processing`, `started_at=now()`, `attempts=attempts+1`.
- [ ] Para cada job, `pg_net.http_post` para `assertiva-enrich` com header `Authorization: Bearer <service_role do Vault>` e body `{ cnpj, leadId, jobId }` (cnpj via join `app.leads`).
- [ ] cron `enrichment-jobs-worker` (`*/1 * * * *`) → `select app.dispatch_enrichment_jobs(...)`.
- [ ] **Kill-switch:** drenagem de `normal` pausável (via parâmetro/setting) sem afetar o realtime.

### AC-3 — Edge function dual-mode + paralelização
- [ ] `assertiva-enrich` aceita `jobId` opcional no body (`index.ts:710`).
- [ ] **Given** `jobId` presente, **when** o pipeline conclui, **then** a função faz UPDATE do job → `done`, `finished_at`, e registra `app.enrichment_runs`; no `catch`, → `failed`/`retrying` (por `attempts`) com `error` preenchido.
- [ ] **Given** chamada sem `jobId`, **then** comportamento legado preservado (compat).
- [ ] Cascata por sócio paralelizada (pool de concorrência = 3) + sleeps redundantes removidos (mantido throttle mínimo anti-rate-limit). Meta: lead com ≤5 sócios conclui < 60s.

### AC-4 — Reaper (resiliência)
- [ ] cron `enrichment-jobs-reaper` (`*/5 * * * *`): job `processing` há > 4 min → `retrying` se `attempts < 3`, senão `failed` com `error='timeout/stuck'`.

### AC-5 — Front: enfileira + polling (sem travar)
- [ ] `socioService.runDeepEnrichment` chama a RPC `request_enrichment` e retorna `job_id` imediatamente (sem esperar a cascata).
- [ ] Hook `useEnrichmentJob(leadId)` faz polling (5s) ou Realtime subscribe em `app.enrichment_jobs`; expõe `status`.
- [ ] `TabSocios.tsx` (botão `:404`) e `CompanyPage.tsx` (`:256`): estado "Na fila / Enriquecendo" com spinner (não bloqueia navegação). **Given** `status=done`, **then** chama `carregar()` e recarrega os sócios. **Given** `status=failed`, **then** toast de erro (tom comercial, sem travessão).
- [ ] **Zero `net::ERR_FAILED`** no fluxo de re-enriquecimento.

### AC-6 — Segurança e custo
- [ ] service_role key + project_url guardados no **Vault** (não em texto no SQL do cron).
- [ ] Drenagem inicia conservadora (budget 3/ciclo) e é pausável.
- [ ] Nenhuma credencial Assertiva nova exposta; RLS de `enrichment_jobs` permanece restrita.

## Riscos & Rollback

| Risco | Mitigação |
|---|---|
| Rate-limit Assertiva na paralelização | Pool limitado a 3 + throttle mínimo mantido |
| `pg_net` async não retorna erro ao cron | Reaper marca stuck (AC-4); edge fecha job (AC-3) |
| **Custo Assertiva ao drenar 746** | Budget 3/ciclo + kill-switch (AC-2/AC-6); realtime isolado da drenagem |
| Edge estoura 150s mesmo paralelizada (QSA gigante) | Reaper → retrying; pool reduz drasticamente; fora-do-clique não afeta UX |
| Regressão no caminho legado | Edge mantém compat sem jobId (AC-3) |

**Rollback:** `cron.unschedule('enrichment-jobs-worker')` + `unschedule('enrichment-jobs-reaper')` para o gasto na hora; edge sem jobId volta ao comportamento atual; migrations revertem por `DROP FUNCTION`. App não depende do worker para nada além do enriquecimento.
