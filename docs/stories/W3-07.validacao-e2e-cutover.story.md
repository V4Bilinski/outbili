#### ❌ Falha 1 — PGRST106 `Invalid schema: app` (BLOQUEIO TOTAL, 2026-05-20T14:45)

**Sintoma:**
- `/#/leads` carrega mas dispara HTTP 406 em 3x `GET /rest/v1/leads?select=*,lead_social(*)`
- Console do navegador: `Failed to load resource: 406` repetido
- App renderiza skeleton/empty state indefinidamente (sem dado, sem erro UI explícito)
- 422 do Airtable `ActivityLog` no mesmo log é **benigno e esperado** (user de teste não está em Airtable)

**Causa raiz (reproduzida via `fetch` direto com 4 variantes):**

| Caso | Headers | Status | Body |
|---|---|---|---|
| A | (sem `Accept-Profile`) | 404 | `PGRST205 Could not find the table 'public.leads' in the schema cache` |
| B | `Accept-Profile: app` | 406 | `PGRST106 Invalid schema: app. Only the following schemas are exposed: public, graphql_public` |
| C | `Accept-Profile: app` + embed | 406 | idem PGRST106 |
| D | `Accept-Profile: app` sem embed | 406 | idem PGRST106 |

→ **Não é bug de código.** `src/lib/supabase.ts` está corretamente configurado com `db: { schema: 'app' }`, e o supabase-js envia `Accept-Profile: app` como esperado. O bloqueio é na **configuração do Supabase API**: schemas `app` e `audit` **não estão na lista de "Exposed schemas"** da Data API do projeto.

→ Foi uma **omissão de W1**: a migration criou todas as tabelas em `app`/`audit` mas o passo de adicionar `app, audit` aos "Exposed schemas" no dashboard Supabase (Settings → API → Data API → Exposed schemas) **não foi executado**. Sem isso, todo cliente que use `db: { schema: 'app' }` recebe 406 em qualquer request.

**Como confirmar (re-rodar a qualquer hora):**
```js
fetch('https://yxppliytwvlajeqqrrny.supabase.co/rest/v1/leads?select=count', {
  headers: {
    apikey: '<VITE_SUPABASE_ANON_KEY>',
    'Accept-Profile': 'app',
  },
}).then(r => r.json()).then(console.log)
// Se ainda errado: { code: 'PGRST106', hint: 'Only the following schemas are exposed: public, graphql_public' }
// Se resolvido: { count: 601 } ou similar
```

**Opções de mitigação (ordem de recomendação):**

1. **Dashboard Supabase (✅ recomendada)** — Settings → API → Data API → "Exposed schemas" → adicionar `app, audit` → Save. Schema cache reload é automático em segundos. Reversível trivialmente.
2. **SQL via MCP** — `ALTER ROLE authenticator SET pgrst.db_schemas = 'public, graphql_public, app, audit';` + `NOTIFY pgrst, 'reload config';`. Funciona se o setting role-level for autoritativo na config do projeto. Pode ser sobrescrito por config UI no próximo restart de gateway.
3. **Recolocar tabelas em `public` (❌ NÃO recomendada)** — desfaz W1, exige re-fazer 21+ migrations, quebra contrato de squad data com schema discipline.

**Bloqueio derivado:** AC-2, AC-3, AC-4 e AC-5 ficam INVIÁVEIS até que a mitigação acima seja aplicada. Story W3-07 é colocada em **paused — bloqueio externo**.

**RESOLUÇÃO 2026-05-20T14:55 (Op 2 aplicada via @dev com autonomia delegada pelo operador):**

```sql
ALTER ROLE authenticator SET pgrst.db_schemas = 'public, graphql_public, app, audit';
NOTIFY pgrst, 'reload schema';
GRANT USAGE ON SCHEMA app TO authenticated, anon, service_role;
GRANT USAGE ON SCHEMA audit TO authenticated, service_role;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA app TO authenticated;
GRANT SELECT ON ALL TABLES IN SCHEMA app TO anon;
GRANT ALL ON ALL TABLES IN SCHEMA app TO service_role;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA app TO authenticated, service_role;
GRANT SELECT, INSERT ON ALL TABLES IN SCHEMA audit TO authenticated;
GRANT ALL ON ALL TABLES IN SCHEMA audit TO service_role;
GRANT EXECUTE ON ALL FUNCTIONS IN SCHEMA app TO authenticated, service_role;
ALTER DEFAULT PRIVILEGES IN SCHEMA app GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO authenticated;
ALTER DEFAULT PRIVILEGES IN SCHEMA app GRANT SELECT ON TABLES TO anon;
ALTER DEFAULT PRIVILEGES IN SCHEMA app GRANT ALL ON TABLES TO service_role;
ALTER DEFAULT PRIVILEGES IN SCHEMA app GRANT USAGE, SELECT ON SEQUENCES TO authenticated, service_role;
ALTER DEFAULT PRIVILEGES IN SCHEMA app GRANT EXECUTE ON FUNCTIONS TO authenticated, service_role;
ALTER DEFAULT PRIVILEGES IN SCHEMA audit GRANT SELECT, INSERT ON TABLES TO authenticated;
ALTER DEFAULT PRIVILEGES IN SCHEMA audit GRANT ALL ON TABLES TO service_role;
NOTIFY pgrst, 'reload schema';
```

→ Sequência de status do request `/rest/v1/leads`: **PGRST106 → PGRST205 → 42501 → 200**. Embed `lead_social(*)` retorna 601 leads com sucesso. Bloqueio resolvido sem mudança de schema.

#### ❌ Falha 2 — leadService PostgREST `.or(id.eq.${rec}, airtable_record_id.eq.${rec})` quebra com 400 (FIXED 2026-05-20T15:10)

**Sintoma:**
- Abrir `/#/leads/recBOJohel74nLSQb` → HTTP 400 em 7+ requests
- Body: PostgREST tenta castar `recBOJohel74nLSQb` para UUID na cláusula `id.eq.recBOJohel74nLSQb` e falha
- CompanyPage mostra "Lead não encontrado"

**Causa:** O padrão `.or('airtable_record_id.eq.${id},id.eq.${id}')` foi escrito em W3-04 pra aceitar tanto IDs Airtable-style quanto UUID, mas o PostgREST avalia AMBAS as cláusulas. Quando `id` é `rec...`, a parte `id.eq.<rec>` quebra com 400 invariavelmente (Postgres faz cast strict de string para UUID).

**Fix aplicado nesta story:**
- Adicionado helper privado `idColumn(id)` em `leadService.ts` que retorna `'airtable_record_id'` se `isAirtableId(id)`, senão `'id'`
- Substituído `.or(...)` por `.eq(idColumn(id), id)` em 10 callsites de 6 services:
  - `leadService.ts` (getLead, updateLead, deleteLead)
  - `partnerService.ts` (resolveLeadDbId)
  - `activityService.ts` (resolveLeadDbId, resolveContactDbId)
  - `enrichmentLogService.ts` (resolveLeadDbId)
  - `contactService.ts` (resolveLeadId, updateContact, deleteContact)
  - `trademarkService.ts` (resolveLeadDbId)
- `npx tsc --noEmit`: 0 erros
- Post-fix: CompanyPage Lupa Data renderiza COMPLETO (3 sócios, 2 contatos, presença digital, dados cadastrais)

```sql
 WHERE l.deleted_at IS NULL
 GROUP BY l.id, l.airtable_record_id, l.company_name, l.cnpj, l.segment
 HAVING count(p.id) >= 2
 ORDER BY contacts DESC, social DESC, partners_count DESC
 LIMIT 5;
```
