### ⏳ Escopo desta story (Zonas Amarela + Vermelha)

## 🟡 Zona Amarela — Identidade `airtable_record_id` → UUID

**Problema:** `airtable_record_id` (formato `rec` + 14) é chave funcional em **15 tabelas** `app.*` e em **59 usos** dentro de **9 services** do frontend. `generateRecordId()` ainda **cria** IDs sintéticos `rec...` em inserts; `isAirtableId()` decide a coluna de busca (`airtable_record_id` vs `id`).

**Tabelas com `airtable_record_id`:** leads, contacts, activities, campaigns, lead_partners, lead_trademarks, profiles, sales_reps, segments, pipeline_events, enrichment_runs (+ `airtable_bridge_log`, `migration_state`, `campaign_targets.message_airtable_id`).

**Services afetados:** leadService, contactService, partnerService, trademarkService, activityService, enrichmentLogService, campaignMetaService, socioService, pescaService.

**Plano (incremental, sem big-bang):**
1. Auditar quantos registros ainda são referenciados por `rec...` no frontend (URLs, deep-links, libs salvas).
2. Garantir que todo registro tem `id` UUID canônico (já têm — `id uuid` é PK).
3. Trocar `generateRecordId()` por `crypto.randomUUID()` em inserts novos (parar de gerar `rec...`).
4. Migrar os helpers: `resolveLeadRef()` passa a aceitar só UUID; manter shim temporário `isAirtableId()` que loga uso (telemetria) para achar consumidores restantes.
5. Quando telemetria zerar por 30 dias: remover `isAirtableId`/`generateRecordId` e as queries `.eq(airtable_record_id...)`.
6. (DB) manter `airtable_record_id` como coluna read-only de auditoria OU dropar após confirmar 0 consumidores.

**Risco:** médio. Quebra deep-links antigos e qualquer integração externa que referencie `rec...`. **Mitigação:** shim + telemetria antes de remover.

## 🔴 Zona Vermelha — Inbox de mensagens (FDW Airtable)

**Problema:** `app.lead_inbox_view` faz `LEFT JOIN airtable_fdw.messages m ON m.leadId = l.airtable_record_id`. **As mensagens do inbox WhatsApp ainda vivem no Airtable** e são lidas via Foreign Data Wrapper. A feature `/inbox` (InboxPage, useInbox, inboxService, ChatPanel...) depende disso. Remover o FDW **quebra o inbox**.

**Plano (migração de dados + reaponte):**
1. Criar `app.messages` (e `app.conversations` se aplicável) no schema Supabase, espelhando o modelo de `airtable_fdw.messages` (campos: leadId, status, content, sentAt, deliveredAt, readAt, airtable_id...).
2. ETL: `INSERT INTO app.messages SELECT ... FROM airtable_fdw.messages` (transacional, como nas waves anteriores).
3. Repontar a origem das mensagens novas: o webhook BilinskiZap/WhatsApp passa a gravar em `app.messages` (hoje grava onde? validar — pode ser n8n/bridge ainda).
4. Reescrever `app.lead_inbox_view` para join em `app.messages` (por `lead_id` UUID, não `airtable_record_id`).
5. Validar o inbox end-to-end (lista, thread, status, envio).
6. Só então: remover `airtable_fdw.messages` do uso; desativar o FDW server `airtable_server`; remover `vault.secrets` (`airtable_pat`).

**Risco:** alto. Inbox é feature viva. **Mitigação:** dual-read (view com COALESCE app.messages + fdw) durante transição; só cortar o FDW após app.messages provar paridade.

## Acceptance Criteria

- [ ] AC1: Nenhum insert do frontend gera `airtable_record_id` no formato `rec...` (usa UUID).
- [ ] AC2: `isAirtableId`/`generateRecordId` removidos após telemetria zerar consumidores.
- [ ] AC3: Mensagens do inbox servidas por `app.messages` (Supabase), não por `airtable_fdw.messages`.
- [ ] AC4: `app.lead_inbox_view` não referencia `airtable_fdw` nem `airtable_record_id`.
- [ ] AC5: Webhook de mensagens novas grava em `app.messages`.
- [ ] AC6: FDW `airtable_server` desativado e `vault.secrets.airtable_pat` removido — **sem quebrar inbox**.
- [ ] AC7: `git grep -i airtable src/` retorna 0 (exceto comentários históricos de migração).

## Sequência segura (ordem obrigatória)

```
Vermelha primeiro (inbox) → depois Amarela (identidade) → por fim drop do FDW
```
Racional: enquanto `lead_inbox_view` usar `airtable_record_id`, não dá para remover a coluna. Migrar o inbox primeiro destrava a remoção da identidade.
